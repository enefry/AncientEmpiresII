# 远古帝国 II：iOS 重制需求文档

版本：1.0  
日期：2026-10-01  
状态：需求基线；实现规划已保存至 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)，iOS 工程与 m0 可玩纵向切片已开始实现。

## 1. 项目目标与已确认方向

用户希望把自己喜爱的老手机游戏《远古帝国 II》（Ancient Empires II）重新做成能在现代设备上运行的游戏，保留原版的玩法、资源、剧情和视觉感受，并能在后续实现每个细节时查到原版依据。

本次讨论中明确提出的要求如下：

| 编号 | 已确认要求 |
| --- | --- |
| U-01 | 首先只考虑 iOS；macOS 通过 iOS on Mac 运行同一应用。 |
| U-02 | 先还原代码参考，不凭记忆从头设计一个相似游戏。 |
| U-03 | 根据职责重新命名混淆类，便于持续阅读和逐项参考。 |
| U-04 | 结合用户提供的 `AEIIRM_src`，与选定 JAR 交叉研究。 |
| U-05 | 先还原游戏设定、算法和游戏资源，再做代码规划与实现。 |
| U-06 | 剧情不仅要有文本，还需要对齐触发条件、位置、状态和时机。 |
| U-07 | 启动画面动画是重点，要求找到原算法并以 100% 还原为目标。 |
| U-08 | 将讨论整理为完整 Markdown 需求文档保存，然后再开始代码规划。 |
| U-09 | 应用界面使用纯 UIKit，不使用 SwiftUI。 |

产品目标是忠实重制。现代化主要解决设备兼容、触摸操作、窗口适配和数据保存；不能在未记录决策的情况下改变兵种数值、关卡条件、AI 行为或动画算法。

本文件规定“要还原什么、如何判断完成”。具体模块、接口和任务拆分见 [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)。用户已确认应用与游戏画面均使用纯 UIKit，不使用 SwiftUI 或 SpriteKit；图形由 UIKit 视图、Core Animation 图层和 Core Graphics 像素栅格承载。最低 iOS 17 仍为建议，不能视为用户已确认的最低系统。

### 2.2 证据与产品选择

每一项还原结果需要区分以下状态，不能混用：

| 状态 | 代表什么 |

| 源码已分析 | 已读懂反编译逻辑和调用链，尚未证明全部与选定包一致。 |

| 设备运行已验证 | 在具体 iPhone、iPad 或 iOS on Mac 上验证了实际表现。 |
| 产品差异 | 为现代平台有意改变的行为，记录原行为、改变理由和验收标准。 |
| 待确认 | 存在未知项，不能作为原版事实写入实现。 |

原包数据、文字描述与运行代码冲突时，先记录差异，按选定基准的实际行为核对，不能只依据说明文字实现。用户明确提出的重制目标可以覆盖原包配置，但这类调整仍应登记为产品差异。

## 3. 平台、范围与交付顺序

### 3.1 平台要求

- 首要运行平台为 iOS，首个完整流程以 iPhone 为验证对象。
- macOS 使用支持 iOS on Mac 的 Apple Silicon Mac 运行同一 iOS 应用，不以独立 macOS 或 Mac Catalyst 工程作为本轮目标。
- iPad 适配列入建议范围；与首版同步交付还是后续补齐，需要在代码规划中明确。
- 最低 iOS 版本、最低设备规格、横屏策略和 Mac 窗口能力尚未确定。
- iOS on Mac 操作必须考虑鼠标、拖动和键盘，不能依赖触摸专用操作、振动或固定全屏尺寸。

### 3.2 完整游戏的建议范围

下列范围由已有原版内容与“忠实重制”目标整理而来，是下一步规划的需求基线；没有把此前未讨论的扩展功能默认为已获确认。

| 范围 | 完整重制的目标 |
| --- | --- |
| 启动与主界面 | 保留重点标题动画，恢复封面、进入游戏和菜单流程。 |
| 战役 | 8 关地图、初始化、教程、对话、剧情、增援、胜败与结局。 |
| 兵种与规则 | 12 种单位、特殊能力、升级、移动、战斗、建筑、经济和回合。 |
| AI | 原版战略选择、评分、行动顺序、招募和特殊关卡行为。 |
| 自由对战 | 12 张地图，真人 / CPU / 关闭阵营、队伍和经济参数；建议保留本地轮流操作。 |
| 视觉与声音 | 原图、精灵序列、地图与侧面战斗演出、原音乐及已确认的声音触发。 |
| 游戏保存 | 战役进度、对局、设置与可靠恢复；具体槽位数量和入口待规划。 |
| 资料系统 | 可持续参考原代码、资源、算法和证据，支持核对未来实现。 |

建议首版以离线游戏为基础，运行时无需下载原资源或登录服务。在线多人、排行榜、广告、内购、账号和云同步未在讨论中提出，不列入当前基线。

v2.5 的地图编辑、导入导出、开发控制台和旧网络入口已经在原版资料中发现，但是否纳入产品需要另行决定。旧网络功能不能因为原代码存在就自动接入。原版 J2ME 存档导入也不是当前已确认要求。

### 3.3 推进顺序

| 阶段 | 目标 | 完成判断 |
| --- | --- | --- |
| R0 资料还原 | 保存代码参考、资源、设定、算法与未知项 | 资料可检索、可复现，证据等级准确。 |
| R1 需求与代码规划 | 完成本需求文档，随后形成技术与实施方案 | 明确模块职责、数据契约、实现顺序、验证方法和未决项处理。 |
| R2 第一关完整流程 | 启动、进入第一关、基本规则、AI、教程与增援、胜败、保存恢复 | 从入口到胜利或失败可以走完，具备原版对应证据。 |
| R3 全量游戏内容 | 其余战役、全部兵种、自由对战和完整表现 | 8 关逐项验收，12 张自由对战地图可使用。 |
| R4 平台与分发验证 | 屏幕适配、输入、音频生命周期、性能、iOS on Mac | 分平台记录实测结果；分发方式确定后再准备对应交付。 |

第一关是实施中的最小完整流程，不代表将完整游戏目标缩减为一关。资料仍有未知项不应被隐藏；也不要求在规划之前先恢复所有厂商 API 或极端旧版错误。

## 4. 用户流程与功能需求

### 4.1 启动和进入游戏

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| FR-BOOT-01 | 游戏资源可从本地加载，进入可操作界面。 | 无网络也能完成启动；失败有明确反馈，不能停留在无说明的空白画面。 |
| FR-BOOT-02 | 保留用户喜欢的标题扭动展开，按原算法还原。 | 逐进度裁切、波形、取整和完整显现符合第 5 节。 |
| FR-BOOT-03 | 标题展开之后恢复人物背景淡入、标题扫光和按键提示。 | 层叠顺序、状态推进、计时与基准对应；字体差异单独报告。 |
| FR-BOOT-04 | 支持触摸或 Mac 输入从封面进入菜单。 | 进入菜单的输入不被当成第二次菜单选择；跳过动画的具体时机需要核对原版并确定产品策略。 |
| FR-BOOT-05 | 启动动画可在后续实现中独立复查。 | 固定逻辑尺寸、进度和时间步时，可与参考帧比较。 |

所选 JAR 的 `Disable-Intro:true` 会跳过文字展开，但用户明确要求保留该动画。重制必须提供该动画，推荐首次正常启动播放；每次是否播放、是否允许跳过、是否保留前情介绍，仍待明确。

### 4.2 菜单、关卡与对局设置

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| FR-MENU-01 | 提供进入战役、继续对局、自由对战和设置的清晰路径。 | 每个已交付模式从主菜单可到达，可返回且不丢失未确认的对局状态。 |
| FR-MENU-02 | 战役入口与进度管理遵守核对后的原版解锁规则。 | 不因解析了 8 张地图就默认为首次可选择全部关卡；解锁与保存行为有来源。 |
| FR-MENU-03 | 进入关卡时显示对应任务名、目标与剧情。 | 任务名、地图名、地图 ID 和文本 ID 分别对应，不能互相替代。 |
| FR-MENU-04 | 自由对战支持阵营类型、队伍、起始金币和单位上限配置。 | 使用已确认配置范围，队伍与颜色独立，关闭玩家的建筑和单位按原逻辑处理。 |
| FR-MENU-05 | 原圆形菜单的展开与旋转效果需纳入表现还原清单。 | 半径、角度、收敛、选中状态和输入中断有对照依据；当前仅定位代码，未完成回放验证。 |

圆形菜单在现代产品中是否直接作为主要操作控件，需要后续规划决定；不能因此删掉其原版视觉资料，或提前声称录屏末尾菜单已经完整还原。

### 4.3 战场显示与操作

玩家在自己的回合选择单位，查看范围，选择目的地，再执行攻击、占领、修复、召唤或待机，也可以直接结束回合。具体“取消移动”能回退到哪一步，以原版流程核对结果为准。

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| FR-MAP-01 | 地形、建筑、单位、阵营与状态准确显示。 | 图块使用 24×24 原始逻辑像素；Tile ID 与地形 Type ID 不混用。 |
| FR-MAP-02 | 区分单位身份、血量、等级、行动状态与特殊效果。 | 信息可读，不能只凭颜色识别敌友、阵营或是否已经行动。 |
| FR-INPUT-01 | 点选单位后显示合法移动与攻击范围。 | 范围与规则结果一致，不允许点选未轮到的敌方单位后直接控制。 |
| FR-INPUT-02 | 提供确认、取消、待机、结束回合等必要操作。 | 操作可恢复到明确状态，不能重复执行伤害、购买或回合切换。 |
| FR-INPUT-03 | 大地图可以拖动查看；缩放策略在规划中确定。 | 浏览手势结束不误触发移动或攻击；剧情接管镜头时行为明确。 |
| FR-INPUT-04 | Mac 支持鼠标点选、拖动和必要键盘操作。 | 不必模拟多指触摸才能完成一关；方向、确认与取消键映射可验证。 |
| FR-INPUT-05 | 动画、AI 与剧情执行时限制不合法的重复输入。 | 对话、镜头和演出结束后正确恢复可操作状态。 |

### 4.4 核心规则、建筑和经济

以下需求的具体公式以 [SETTINGS.md](../reference/reconstruction/SETTINGS.md) 与 [ALGORITHMS.md](../reference/reconstruction/ALGORITHMS.md) 为规范附件。

| 编号 | 需求 | 必须保留的细节 |
| --- | --- | --- |
| FR-RULE-01 | 还原 12 种单位的配置、等级与特殊能力。 | 原价格、移动预算、攻击区间、防御、射程、属性位、侧面角色数量；水晶不走普通攻击随机路径。 |
| FR-RULE-02 | 还原移动范围、路径、阻挡与取消。 | 剩余预算严格大于 0；地形费用、敌军阻挡、友军穿越、落格合法性与路径平手顺序。 |
| FR-RULE-03 | 还原攻击与反击。 | 随机上界不包含、整数截断、等级与状态加成、HP 缩放、先攻后反击及反击资格。 |
| FR-RULE-04 | 还原死亡、墓碑、指挥官离场与复活。 | 普通兵、骷髅、水晶、指挥官和最终关 Saeth 的路径不同；墓碑按玩家轮转计数。 |
| FR-RULE-05 | 还原中毒、光环和召唤。 | 中毒攻防各减 10，不新增持续扣血或减速；光环触发和清除时点准确；召唤出的骷髅当次行动结束。 |
| FR-RULE-06 | 还原单位行动限制。 | 投石车移动与攻击互斥；移动完成和整次行动结束不能被合并为同一个时点。 |
| FR-ECON-01 | 还原占领、修复、收入与恢复。 | 占领须执行行动；每座城镇 +30、城堡 +50；符合条件的建筑恢复最多 20 HP，封顶 100。 |
| FR-ECON-02 | 还原招募资格、出生位置、资金和单位上限。 | 必须拥有城堡、兵种解锁、金币与可达空格满足要求；上限计算排除骷髅。 |
| FR-ECON-03 | 还原指挥官复活代价与保留属性。 | 保留原等级 / 经验与对象身份语义；每次死亡价格递增逻辑不能替换成固定购买价。 |
| FR-TURN-01 | 还原玩家轮转、跳过、收入、效果清除和恢复顺序。 | `currentTurn` 按每次玩家切换增加，不能改为每完整一轮增加。 |
| FR-END-01 | 按各模式与各关代码条件判定胜败。 | 不使用统一“敌军全灭”替代所有条件，也不直接照任务文字推断失败。 |

原版没有确认的功能不能自行添加，例如视线遮挡、距离伤害衰减或墓碑立即永久清除。极端的整数绕回、损坏存档或旧版错误另列兼容性决策；“忠实重制”不等于故意引入崩溃和无法恢复的数据损坏。

### 4.5 战役剧情、教程与触发

完整要求包括静态地图之外的初始化和实时剧情。每关建立可审查的对应表，至少包含：关卡 ID、前置状态、触发条件、事件语义、坐标 / 区域、对话与头像、单位引用、出生 / 移动 / 删除、镜头和等待、操作启停、后继状态、胜败与存档恢复行为。

| 编号 | 需求 | 验收条件 |
| --- | --- | --- |
| FR-STORY-01 | 还原 8 关初始化、剧情与结局。 | 地图原始单位和开场后可控部队分别核对，不能将 `.aem` 预览当正式开局截图。 |
| FR-STORY-02 | 对齐触发区域、行动事件和状态顺序。 | 同一坐标在错误状态、经过但未结束行动、错误阵营等情况不能提前触发。 |
| FR-STORY-03 | 保留状态外的全局剧情检查。 | 不能只移植 213 个 `case` 摘录而漏掉水晶死亡、初始化、Saeth 死亡标志等判断。 |
| FR-STORY-04 | 对话与头像按原 ID 关联。 | 头像 ID、指挥官变体与阵营颜色体系分开；不凭兵种名重新分配角色。 |
| FR-STORY-05 | 等待、移动和镜头会影响剧情推进。 | `moveMapAndCursor` 隐式推进状态、逻辑等待步数、对话暂停、结束行动事件清理均有对应。 |
| FR-STORY-06 | 保存恢复后不漏触发或重复剧情。 | 已执行的增援、对话、删除、目标切换和任务完成不会重放；未执行事件仍能触发。 |
| FR-STORY-07 | 资料浏览可显示剧情触发区域和状态说明。 | 清楚标出前置状态与坐标范围，区分触发区、出生点、移动终点、镜头目标；仅标图不代表已运行验证。 |

重点验收例子：

| 关卡 | 必须覆盖的行为 |
| --- | --- |
| m0 第一关 | 教程与第一批敌人清空后继续增援，不能提前判定胜利；第二批结束后才推进完成。 |
| m1 第二关 | 地图外部队入场、占领教程、指挥官死亡与复活教程前置条件；胜利检查同时考虑红军与红城堡。 |
| m2 第三关 | 蓝方单位结束行动后满足 `x≤4 或 y≤10` 才触发相关伏击；地图外出生与元素生物换阵营。 |
| m3 第四关 | 援军、镜头、投石车毁城镇与修复教程；不凭“保护神庙”的文字新增未经确认的失败检测。 |
| m4 第五关 | 四组依次受状态限制的区域伏击、水晶死亡失败；状态 25 支持水晶抵达区域或红军全灭的完成路径。 |

## 5. 启动动画的专项还原与验收

这是用户明确指出的重点，不能用视觉上近似的缩放、扭曲滤镜或系统缓动替代原算法。

### 5.1 精确逻辑要求

- 使用原 `logo.png`（240×85）、`splash.png`（240×320）和 `glow.png`（67×78）。
- 逐像素行裁切完整 Logo，展开进度为 `p=0…40`；窗口逐步变宽，各行横向位移，字形本身不被横向压缩。
- 保留整数递推的 360 项正弦表，不能直接替换为系统 `sin()`。
- 保留 Java 负数除法向零截断，以及位移 `>>10` 的算术右移语义。
- 240×85 时可见宽度为 `6p`，波幅为 `240×(40−p)/160`，首行相位为 `9p`，每行相位增加 `360/85=4`，均使用整数运算。
- 状态 3 的进度超过 40 后进入状态 4，背景淡入 `q=0…16`；黑色覆盖 alpha 为 `255×(16−q)/16`，Logo 保持清晰。
- 保留完整 Logo → 扫光 → splash → 提示文字的稳定绘制顺序；扫光必须受 splash 遮挡。
- 240 像素画布下扫光位置从 −67 开始，每次移动 40，达到 / 超过 `画布宽×4` 后重置；不能刚离开 Logo 就循环。
- 提示文字显隐、字体和描边独立核对；圆形菜单的展开与旋转另有算法和输入中断。

原版目标更新间隔为 `1000/15=66` 毫秒，逻辑计数每次加 50；不能把这两者混为一谈。现代显示刷新与原动画推进需要独立，具体调度方式在代码规划中确定。

### 5.2 “100%”的验收分层

| 层次 | 验收标准 | 当前状态 |
| --- | --- | --- |
| 资源 | 基准图片字节、尺寸、透明区域一致 | 已验证。 |
| 波形算法 | 固定输入时全部裁切与绘制位置一致，整数运算一致 | 原 JAR 函数隔离执行；369 组 / 31,980 行指令比较差异为 0。 |
| 状态与命令 | 展开、淡入、扫光、闪烁的条件、更新和绘制命令一致 | 正常标题路径已隔离执行并记录；不等于完整手机运行。 |
| 逻辑像素 | 固定画布与透明混合规则下，逐帧像素一致 | 有参考回放；尚未验证 J2ME 平台透明混合和系统字体。 |
| 实际录屏 | 明确包、配置、画布、输入与时间轴后对齐画面 | 已比对形状和约 66 ms 节奏；未完成逐像素、逐时刻一致性验证。 |
| iOS 实现 | 同输入输出对应帧、状态、时序，并在设备上核对 | 纯 UIKit app 与 m0 基本战役流程已实现；启动逐帧一致性、原版 AI / 战斗演出和设备核对仍未完成。 |

当前录屏对应版本 / 配置未知，且录屏播放了所选包默认跳过的展开。在此差异确认之前，不能把“算法指令一致”扩大为“整段录屏 100% 一致”。字体、圆形菜单、音源、全启动前情和输入时点的缺口保留到验收清单。
